PROBLEM STATEMENT
The physical lab has no centralised virtual machine repository. Each session requires manual OS installation on individual machines. There is no snapshot or rollback mechanism — a corrupted VM means a full reinstallation, wasting class time and lecturer effort.
RESEARCH QUESTIONS
  1. How can a single Dell R440 server serve as a centralised image repository for the Acer edge Proxmox nodes (10 Ceph nodes + 1 T-Pot host) simultaneously?
  2. What thin-provisioning and snapshot strategy minimises storage consumption while supporting rapid VM rollback?
  3. What are the minimum VM specifications (RAM, vCPU, disk) needed for each course type to function adequately on Acer hardware?
SCOPE & TASKS
  1. 01Install and configure Proxmox VE on Dell R440 and connect the 11× Acer Predator nodes (10 Ceph cluster nodes, 1 dedicated to T-Pot) (DONE as of Sep 2026); partition storage for image repository vs running VMs.
  2. 02Create 7 golden VM images: Ubuntu Server 22.04, Windows Server 2022 + AD, DVWA, Kali Linux 2024, OPNsense, Docker Host, Windows 10 workstation. Build order: Ubuntu, Kali, DVWA first (cover most classes); the rest follow as time allows. Keep a spare-capacity note for a T-Pot host (FYP-3A).
  3. 03Implement thin provisioning (Proxmox linked clones) and automated daily snapshot strategy.
  4. 04Document image creation SOP and produce capacity planning report (max concurrent VMs given RAM/storage).
  5. 05Build and test backup/restore automation scripts; measure boot time benchmarks per image type.
METHODOLOGY
Action Research Benchmarking Iterative Build Documentation
Build-test-document cycle. Each VM image is built, snapshot tested, stress-tested for boot time, and documented before being considered production-ready. Capacity planning uses empirical RAM/CPU measurements under load.

HOW THIS SECTION ENABLES OTHERS
FYP-1C (Automation) cannot push images without the image repository. FYP-2A/2B/2C cannot run exercises without the VM templates. FYP-2A (LabEye) reads the Proxmox API that I configure and deploys from my templates via 1C. FYP-3A (Honeypot) runs on a T-Pot VM built on the same Proxmox base, and FYP-3B (IDS/IPS) tunes against traffic from these images. There is no separate portal phase: LabEye (2A) is the dashboard and deploy front-end, so I keep the API and template naming stable for it. My golden images define what every student in every class works with — this is the foundational layer.
