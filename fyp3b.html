PROBLEM STATEMENT
The lab's OPNsense gateway has no active intrusion detection or prevention capability. Red Team attacks pass through the network perimeter undetected and uninspected. Without an IDS/IPS tuned to the lab's specific attack scenarios, no network-layer detection is possible. Wazuh (1B/2A/2C) already covers host and log data, so this project covers only the network layer — and the Palo Alto XDR cloud dependency adds a licensing cost risk.
RESEARCH QUESTIONS
  1. How should Suricata be deployed (inline IPS vs TAP IDS) within OPNsense to balance detection coverage with performance overhead at 1 Gbps throughput?
  2. What custom Suricata rules are needed to reliably detect the ATT&CK-mapped scenarios delivered by FYP-2B without generating excessive false positives?
  3. How can Suricata alerts reach the existing Wazuh deployment (1B / 2A / 2C) with the least new plumbing, so network and host alerts can be correlated?
SCOPE & TASKS
  1. 01Deploy Suricata inside OPNsense — evaluate inline IPS mode vs TAP mode for the lab environment; document trade-offs.
  2. 02Write custom detection rules for the FYP-2B scenarios (rule set kept small and versioned): Metasploit signatures, SQL injection patterns, Nmap scan detection, C2 communication patterns.
  3. 03Performance tune Suricata: whitelist legitimate lab management traffic, optimise rule set to maintain <5% CPU overhead.
  4. 04Forward Suricata alerts into the existing Wazuh manager (eve.json via the Wazuh agent on OPNsense or a syslog input). Wazuh is not rebuilt here; 3B only adds the network-layer source and any 2C-style custom rules/decoders it needs.
  5. 05Create rule management SOP — how to add/update/disable rules as new attack scenarios are introduced.
