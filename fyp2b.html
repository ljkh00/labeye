PROBLEM STATEMENT
01 · LACK OF SCALABLE HANDS-ON TRAININGUniversities struggle to provide scalable hands-on cybersecurity training. Traditional labs rely on manual setup and instructor involvement, so consistent Red Team experience cannot be delivered to large student cohorts.
02 · NO EDUCATION-FIT AUTOMATION LAYERCyber ranges supply infrastructure but not a lecturer-facing control layer. Commercial platforms (e.g. Cyberbit) are costly; adversary-emulation tools (e.g. CALDERA) assume the lab already exists.
03 · MANUAL ENVIRONMENT SETUP OVERHEADLecturers still clone VMs, configure networks, install vulnerable services, verify connectivity, issue access, and repeat this across workstations. Misconfiguration causes lab failure; reset is slow for a full class.

Refined problem: a lecturer-focused orchestration platform that automates provisioning, configuration, multi-seat deployment, access, and teardown — without the lecturer managing every VM or hypervisor task.

PROBLEM SOLUTION

Build a lecturer-facing orchestration platform whose core is the recipe / scenario engine, not the hypervisor clone. The lecturer picks service recipes, vulnerability recipes, and scenario modules. The orchestrator resolves dependencies, generates Ansible/cloud-init artefacts, tracks status, and verifies that the teaching service actually came up.

Cloning and linked-clone rollout are delivery support on Proxmox. Students never log into the hypervisor. They open an opaque console URL bound to their seat. Each Lenovo runs update_workstation_ip.ps1 so the backend knows which IP is which workstation. A console token issued for ws1 cannot be reused on ws2.

MITRE ATT&CK IDs live as recipe metadata. The platform does not auto-execute attacks — it composes, verifies, and delivers the lab.

RESEARCH QUESTIONS
  1. How can a lecturer-focused orchestration platform be designed to configure and deploy customisable cybersecurity lab scenarios using reusable VM templates and modular recipes within a controlled and isolated university environment?
  2. To what extent can an automated orchestration workflow reduce the time and complexity involved in cloning base templates, applying scenario-specific configurations, and provisioning lab VMs in a repeatable manner?
  3. How can the configured lab scenarios be structured using selected cybersecurity tools and mapped to the MITRE ATT&CK framework so that the resulting exercises are realistic, pedagogically organised, and aligned with a recognised model of adversary behaviour?
PROJECT OBJECTIVES
  1. Design and develop a lecturer-focused platform for configuring and deploying customisable cybersecurity lab scenarios using reusable VM templates and modular recipes within a controlled and isolated university environment.
  2. Implement an automated orchestration workflow that clones base templates, applies scenario-specific configurations, and provisions attacker and victim VMs through infrastructure automation tools, in order to reduce manual setup effort and improve repeatability.
  3. Integrate scenario components with selected cybersecurity tools and map the configured attack scenarios to the MITRE ATT&CK framework so that the resulting lab exercises are structured, realistic, and aligned with a recognised standard for adversary behaviour.

SYSTEM LOGIC — ORCHESTRATOR IS THE CORE

Cloning VMs is supporting infrastructure. The distinctive logic is: compose a lab from YAML recipes, run it through the orchestrator, verify the teaching service, then bind opaque console access to a workstation IP.

01 · CORE
Catalogue & compose Load YAML service, vulnerability, and scenario recipes. Resolve dependencies (e.g. SQLi pulls web + DB). Reject unknown recipes / OS mismatch before anything is cloned.
02 · SUPPORT
Place & clone Not the product core. Proxmox linked-clone of golden templates, VLAN tags, cloud-init SSH key. Memory gate skips overloaded Acer nodes.
03 · CORE
Configure Wait for guest IP then real SSH. Recipe engine generates Ansible. Runner executes the playbook with lock/timeout handling.
04 · CORE
Verify Ansible exit 0 is not “ready”. DeploymentVerifier HTTP-checks the recipe. Fail = lecturer sees verification failed, not a false ready seat.
05 · CORE
Bind & grant Register seat → VM. Mint opaque /console/<token>. Client IP must match the workstation heartbeat. Teardown revokes tokens.

RECIPES / SCENARIOS — RECIPE ENGINE

Three YAML layers, kept as data so new labs do not rewrite Python:

  • Service recipes — supporting stack (web server, database, etc.).
  • Vulnerability recipes — the teaching flaw, with ATT&CK IDs and HTTP verify checks.
  • Scenario modules — a class activity: which packages, which VM roles (attacker / victim / C2), which template.

recipe_engine.py loads the catalogue, resolves dependencies, and generates cloud-init + Ansible artefacts at deploy time. orchestrator.py (single lab) and scenario_orchestrator.py (multi-role, multi-seat) register status, wait for IP/SSH, run the generated playbook, then call the verifier. Lecturers design the activity; they do not reconstruct the stack by hand.

ORCHESTRATOR STATUS PATH

Long deploys run in a background thread. The dashboard polls status — it does not block on a 4-minute first configure. Stages are tracked separately because “clone accepted” is not “lab ready”:

  • Registered in the status registry
  • Power-on waited (not fire-and-forget)
  • Guest-agent IP wait, then SSH wait (up to 180s, real ssh probe)
  • Ansible playbook from the recipe
  • HTTP verify against recipe checks
  • Mark ready or failed — seats that fail do not get console URLs
VERIFICATION & VALIDATION

deployment_verifier.py exists because a successful Ansible run is not enough. The teaching site must actually answer.

PRE-DEPLOY VALIDATION

  • Parse scenario YAML; reject unknown recipes and unknown template_vmid values.
  • OS match (Linux-only recipe cannot land on a non-Linux template).
  • Node memory gate (default 70%) — skip an Acer that would go over after this seat.
  • Golden template VMIDs treated as production assets (wrong VMID clones the wrong lab).

DURING PROVISIONING

  • Status JSON polled by LabEye: provisioning → IP wait → SSH wait → Ansible → verify.
  • VLAN applied before power-on; cloud-init injects the controller SSH key.
  • Playbook timeout + dpkg-lock handling so a hung package install does not fake success.
  • Lecturer sees a failed seat instead of a silent skip.

POST-DEPLOY VERIFY

  • Rewrites recipe URLs (localhost → guest IP) and issues HTTP checks with retries.
  • Soft-matches expected response strings; skips interactive payloads (e.g. reverse shells).
  • Produces a VerificationReport per check.
  • Pipeline distinguishes Ansible failed from Ansible OK, HTTP verification failed so a down PHP/Apache lab is never marked ready.
OPAQUE CONSOLE URLS

Students never receive a Proxmox login, VMID, or VNC endpoint. LabEye asks the lab API for a console URL; the student opens /console/<48-hex-token> on the Node.js noVNC proxy (vnc-proxy-server.js / fyp_proxy).

The token is not guessable and is not a VMID. It is stored in SQLite as token → deployment → VMID → workstation_id, with TTL (default 1 hour) and a revoked flag. Numeric URLs such as /console/301 are rejected so a student cannot change a number and land on someone else’s VM.

On open, the proxy POSTs the token plus the client IP to the lab API. Access is allowed only if the token is valid, the deployment is active, the VMID matches, and the client IP belongs to that workstation. Otherwise the student gets a generic 404 — no grant enumeration. Sessions are one-shot WebSocket upgrades; max two VNC sessions per VM; tickets stay on the server. Power actions use the same opaque token, never a raw VMID.

WHY OPAQUE + SEAT BINDING
  • 01Hide the hypervisor. Browser talks only to the proxy; Proxmox credentials never leave the controller.
  • 02Stop URL tampering. Opaque hex token; VMID is not in the page or in session JSON.
  • 03Stop seat hopping. A token minted for ws1 fails from ws2’s IP even if the URL is copied.
  • 04Default deny + template lockout. Golden/infra VMIDs are never grantable to students.
  • 05Revoke on teardown / TTL / remint so leftover links die with the lab session.
WORKSTATION IDENTITY — update_workstation_ip.ps1

Each student Lenovo runs update_workstation_ip.ps1 (installed under ProgramData, scheduled at logon and every 30 minutes). The script is edited per seat: WorkstationId must match workstations.json (e.g. ws1). It picks the lab LAN IPv4 (preferred prefix 192.168.0., skipping loopback/Docker/WSL) and POSTs identity to the VNC proxy on the student VLAN:

POST http://<proxy>:8080/api/lab/access/workstation-ip  →  { workstation_id, ip, replace_ips: true }

The proxy forwards that into the lab API, which writes the IP onto the seat record. A local ip_heartbeat.log is also shipped to /api/lab/access/workstation-log for troubleshooting. Without this heartbeat, DHCP or a cable move would leave the backend thinking ws1 is still the old address — and console IP checks would deny the real student or, worse, bind the wrong seat.

What is automated

CALDERA automates attack techniques. Cyberbit automates vendor scenario delivery. This project automates VM clone, VLAN tagging, recipe application, post-deploy checks, console grant, and teardown/TTL.

Lab environment setup

Not the core of CALDERA. Vendor-operated in Cyberbit. Core product here: recipe/scenario orchestrator, dependency resolution, and post-deploy verification. Cloning is delivery support.

Cost & access

Runs on the existing faculty Proxmox cluster with no commercial range licence. Students use a browser console; they never receive hypervisor credentials.
