PROBLEM STATEMENT
  • Lack of an automated laboratory environment in cybersecurity education at UOW Malaysia
    Students must manually configure virtual machines which result in inconsistent configurations and setup failures (Al-Zubaidie et al., 2024)
    Traditional on-premises labs face high maintenance costs, limited accessibility, and hardware constraints (Khan & Mohamed, 2025)
    Container-based cyber range platforms still require infrastructure complexity and administrative overhead (Chouliaras et al., 2023)
    EDURange provides browser-based exercises but lacks external device integration and remains dependent on external infrastructure (Lundqvist et al., 2025)
    Students spend excessive time troubleshooting technical setup issues instead of developing practical cybersecurity skills
  • Root cause: absence of a centralized and automated laboratory infrastructure
  • Solution required: leverage automation and Infrastructure-as-Code (IaC) to enable automated cybersecurity lab infrastructure
RESEARCH OBJECTIVES
  1. To integrate Infrastructure-as-Code (IaC) and automation tools such as Terraform, Ansible, and GitLab CI/CD in automating the provisioning, configuration, and lifecycle management of cybersecurity lab environments.
  2. To design and develop a centralized and automated virtualization infrastructure using Proxmox Virtual Environment (VE) to provide standardized cybersecurity lab environments.
  3. To validate the effectiveness of the automated laboratory infrastructure in enhancing practical cybersecurity learning and reducing environment setup issues for students.
RESEARCH QUESTIONS
  1. How can infrastructure automation tools such as Terraform, Ansible, and GitLab CI/CD be integrated to enable efficient deployment, configuration, and management of cybersecurity lab environments?
  2. How can a centralized and automated virtualization infrastructure be designed to support consistent and scalable cybersecurity laboratory environments?
  3. How effective is the proposed automated cybersecurity laboratory infrastructure in improving hands-on learning experiences and reducing setup complexity for cybersecurity students?

CURRENT IMPLEMENTATION & ACHIEVEMENTS

The current prototype implements the complete student virtual-machine lifecycle, from template selection and deployment to configuration, browser-based access, and controlled destruction. The implementation combines a student dashboard with a Flask API, SQLite deployment tracking, GitLab CI/CD orchestration, Terraform linked cloning, Ansible configuration, a Proxmox VE cluster, and a noVNC console proxy. All seven dashboard templates have been verified end-to-end and the Ubuntu Server workflow below is one representative example.

Implemented automation pipeline
01

02
Flask API Authenticates the request, validates quota, and creates a deployment.
03

Implemented capabilities
Seven verified VM templates

Ubuntu Server, Kali Linux, Windows 10, OPNsense, Ubuntu with Docker, Kali with DVWA, and Windows Server can each be deployed, configured, accessed, and destroyed through the same workflow.

Repeatable automated provisioning

Node-local golden templates and Terraform linked clones reduce repeated setup work while Ansible applies a consistent configuration for each lab type.

Reliable deployment tracking

Each request is linked by a unique deployment ID. A background reconciler updates SQLite from GitLab and Proxmox so the dashboard can rebuild the correct VM state after refresh.

Controlled multi-user lifecycle

Backend quota checks, transactional VM-ID reservation, per-deployment state, ownership filtering, status reconciliation, console access, and controlled destruction support safe concurrent student use.

Infrastructure and security handling
SERVER AND WORKSTATION ADDRESSES

Each student workstation has a fixed network identity such as ws2. A workstation-side script reports its address so the backend can map the logged-in student session to the correct workstation and deployment target. Management addresses remain separate from student access data.

ISOLATED STUDENT NETWORK

Deployed lab VMs use VLAN 900 on the isolated 172.29.0.0/24 network. This separates vulnerable lab workloads from the management network while allowing the automation server to configure VMs and proxy console traffic.

VM-ID ALLOCATION AND STATE

The Flask API requests the next available cluster VM ID from Proxmox and reserves it in SQLite within the same transaction as the quota check. This prevents concurrent requests from receiving the same VM ID.

AUTHENTICATED API AND CREDENTIALS

The dashboard uses authenticated endpoints for catalogue, deployment, quota, status, access, console, and destruction operations. API tokens, Proxmox credentials, passwords, and private keys remain in protected server-side configuration or environment variables and are not embedded in this page.

THREE-VM STUDENT QUOTA

One Acer Predator Proxmox node currently serves two student workstations and its SSD supports approximately six concurrent student VMs. The backend therefore limits each student to three active deployments, dividing the available node capacity fairly and reducing storage exhaustion.

BROWSER-BASED CONSOLE

When a VM reaches the running state, the API returns a deployment-specific console URL. The noVNC proxy gives the student graphical access through the dashboard without exposing Proxmox management credentials.

Demonstrated workflow - Ubuntu Server on ws2
STEP 01
Select a verified template

The dashboard loads the backend catalogue and displays the seven available templates. The student session is associated with workstation ws2 before a template is selected.

STEP 02
Confirm the deployment request

The selected Ubuntu Server template, assigned workstation, and deployment quantity are shown for verification before any infrastructure change begins.

STEP 03
Trigger the automated pipeline

After confirmation, Flask records the deployment and triggers GitLab CI/CD. The dashboard immediately identifies ws2 as the workstation receiving the VM.

STEP 04
Track provisioning and configuration

A VM card appears with the current deployment status. Terraform creates the linked clone, Ansible configures it, and reconciliation keeps the SQLite record and dashboard state aligned.

STEP 05
Use the running VM

Once provisioning, configuration, and readiness checks succeed, the status changes to Running and the console and destruction controls become available.

STEP 06
Access the isolated VM console

The Open Console action retrieves the correct VM console URL and connects through the noVNC proxy, allowing the student to interact with the cloned VM without direct access to the Proxmox management interface.

STEP 07
Destroy the environment safely

The dashboard sends the exact deployment ID to the Flask API and prevents duplicate destruction requests while Terraform removes the VM using the same deployment state. The card is removed after destruction completes.

FUTURE ENHANCEMENT

1. Snapshot-Based Lab Destroy

  • Create a verified clean snapshot after the VM has been successfully deployed, configured, and tested.
  • Roll back and restart the existing VM when a student requests a clean environment, avoiding the full clone-and-configure process.
  • Apply snapshot cleanup rules and keep Proxmox, SQLite, and Terraform state synchronized across Linux and Windows VMs.

2. Resource-Aware Node Scheduling

  • Check live CPU, RAM, storage, node availability, and active deployments before starting a deployment pipeline.
  • Select an eligible node with sufficient resources and the required golden template based on each VM template's requirements.
  • Distribute VMs more evenly, reject unavailable nodes clearly, and increase capacity through additional storage or Proxmox nodes.
